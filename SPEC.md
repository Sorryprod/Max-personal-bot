## 1. Продукт

**Проблема.** Владелец небольшого кафе или магазина в Белгородской области ищет
линейный персонал (повар, продавец, официант, курьер, уборщик). Текучка высокая,
вакансию нужно закрывать за дни. Сегодня отклики приходят вразнобой: звонки,
объявления в городских чатах, сообщения в личку. Кандидаты не доходят до
собеседования, часть откликов теряется, а базовые вопросы (возраст, наличие
медкнижки, готовность к графику) работодатель выясняет вручную по каждому.

**Пользователи.**
- Работодатель — владелец или управляющий, 1–3 точки, нет HR-отдела и нет ATS.
- Соискатель — ищет работу рядом с домом, не будет заполнять длинную форму на сайте,
  но ответит на три вопроса в мессенджере.

**Ценность.** Работодатель получает отклики в одном месте, уже отфильтрованные по
стоп-критериям, и назначает собеседование в два нажатия. Соискатель откликается
за минуту и видит статус, а не пропадает в тишине.

**Ограничение области.** Мы не делаем job-борд, не делаем поиск по всей России, не
делаем резюме и не делаем чат между сторонами. Только путь «вакансия → отклик →
скрининг → приглашение на собеседование».

---

## 2. Основной сценарий (это то, что будут проверять)

### Работодатель
1. Открывает бота, выбирает роль «Я ищу сотрудников».
2. Бот в чате спрашивает: название точки, город/район.
3. Бот открывает мини-приложение «Создать вакансию»: должность, график, зарплатная вилка,
   адрес, до 3 отсеивающих вопросов (выбор из шаблонов + свои).
4. После сохранения бот присылает готовую ссылку-приглашение на вакансию,
   которую можно переслать в любой чат.
5. Как только приходит отклик — бот шлёт уведомление.
6. В мини-приложении «Мои вакансии» работодатель видит список кандидатов с ответами
   на отсеивающие вопросы, сравнивает их в одном экране, ставит статус:
   «пригласить», «в резерв», «отказать».
7. При статусе «пригласить» бот отправляет кандидату сообщение с адресом и предложением
   выбрать время из двух-трёх слотов.

### Соискатель
1. Переходит по ссылке-приглашению и попадает в бота.
2. Бот показывает карточку вакансии и кнопку «Откликнуться».
3. Бот задаёт отсеивающие вопросы кнопками (не свободным текстом, где это возможно),
   плюс просит имя и контакт.
4. Бот подтверждает отклик и обещает ответ.
5. При изменении статуса получает уведомление; при приглашении выбирает слот кнопкой.

**Критерий готовности MVP:** оба пути проходятся от начала до конца в MAX без участия
разработчика, на чистой базе, дважды подряд.

## 3. Разделение бот / мини-приложение

Держись этого разделения, оно обосновано в брифе организаторов и будет отдельно
оцениваться.

**В боте:** выбор роли, короткие последовательные вопросы, отклик, все уведомления,
статусы, выбор слота собеседования.

**В мини-приложении:** создание вакансии (длинная форма), список вакансий, список и
сравнение кандидатов, возврат к ранее введённым данным.

Мини-приложение подключается к боту и не должно работать как изолированный сервис.

## 4. Технический стек

- Python 3.12, FastAPI, Uvicorn.
- PostgreSQL 16, SQLAlchemy 2.x (async), Alembic для миграций.
- httpx для вызовов MAX Bot API.
- Мини-приложение: React + Vite + TypeScript, библиотека MAX UI, MAX Bridge для
  взаимодействия с платформой. Сборка статики отдаётся тем же FastAPI.
- Docker + docker compose.

Использовать JS/React для мини-приложения рекомендовано организаторами, для бэкенда
допускается любой язык.

**Не тащи внутрь образа никаких ML-моделей и тяжёлых зависимостей.** LLM в этом MVP
не нужна вообще. Если позже решим добавить — только через внешний API, отдельным
опциональным модулем.

## 5. Архитектура

```
app/
  main.py                 # сборка FastAPI, роутеры, lifespan
  config.py               # pydantic-settings, всё из env
  db/
    models.py             # SQLAlchemy модели
    session.py
    seed.py               # синтетические демо-данные
  max/
    client.py             # ТОНКИЙ адаптер над MAX Bot API — единственное место,
                          # где знают про формат запросов платформы
    webhook.py            # приём апдейтов, валидация, диспетчер
    keyboards.py
  bot/
    router.py             # маршрутизация апдейтов по состоянию диалога
    states.py             # конечный автомат диалога, хранится в БД, не в памяти
    handlers/
      employer.py
      candidate.py
  api/
    vacancies.py          # REST для мини-приложения
    applications.py
    auth.py               # проверка подписи initData из MAX Bridge
  services/
    screening.py          # логика отсеивающих вопросов и статусов
    notifications.py      # отправка уведомлений через max/client
webapp/                   # React мини-приложение
migrations/
tests/
```

**Важные архитектурные требования.**
- Вся специфика MAX изолирована в `app/max/`. Остальной код не знает, что это MAX.
  Если API платформы изменится, чинится один модуль.
- Состояние диалога хранится в PostgreSQL, а не в памяти процесса. Перезапуск
  контейнера не должен ломать незавершённый диалог.
- Обработка апдейтов идемпотентна: повторная доставка одного апдейта не создаёт
  второй отклик. Храни обработанные update_id.
- Любое обращение к MAX API обёрнуто в таймаут и ретрай, падение внешнего вызова
  не роняет обработку апдейта.

## 6. Модель данных (минимум)

- `employer` — max_user_id, имя, название точки, город, created_at
- `vacancy` — employer_id, должность, график, зарплата от/до, адрес, статус, invite_slug
- `screening_question` — vacancy_id, текст, тип (yes_no | choice | text), варианты, is_blocking
- `candidate` — max_user_id, имя, контакт
- `application` — vacancy_id, candidate_id, статус (new | screened | invited | reserve | rejected), created_at
- `answer` — application_id, question_id, значение
- `interview_slot` — application_id, datetime, выбран ли
- `dialog_state` — max_user_id, текущий шаг, контекст (jsonb)
- `processed_update` — update_id, обработан_в

## 7. Требования сдачи (это 60% оценки, отнесись серьёзно)

### Docker
- `Dockerfile` для бэкенда, многоступенчатая сборка, сборка фронта отдельной стадией.
- `compose.yaml`: сервисы `api`, `db`. Одна команда `docker compose up` поднимает всё.
- `.dockerignore`, `.env.example` **без единого реального токена**.
- **Сборка не дольше 5 минут** без учёта скачивания базовых образов. Кэшируй слои,
  не ставь лишнего, не собирай фронт на каждое изменение бэкенда.
- Миграции применяются автоматически при старте.

### Безопасность
- Никаких токенов, паролей и ключей в коде и в git-истории. Всё через переменные окружения.
- Версии всех зависимостей зафиксированы (`requirements.txt` с пинами, `package-lock.json`).
- Данные мини-приложения авторизуются проверкой подписи initData, а не доверием
  к переданному user_id.

### Обработка ошибок и стабильность
- Некорректный ввод пользователя обрабатывается предусмотренно, без трейсбеков в чат.
- После ошибки пользователь может продолжить, а не начинать сначала.
- Мини-приложение показывает состояния загрузки, успеха и ошибки. Пустой список —
  это отдельное состояние с подсказкой, а не белый экран.

### README.md
Обязан содержать ровно эти разделы:
назначение решения; основной пользовательский сценарий; состав и архитектура решения;
одна команда запуска всех локальных компонентов через Docker; необходимые параметры
окружения; переменные окружения; используемые порты; зависимости; внешние сервисы и
интеграции; описание работы с данными; порядок работы с тестовыми данными; пошаговый
сценарий проверки; примеры ожидаемого поведения системы; известные ограничения;
порядок остановки и повторного запуска.

В разделе про данные явно укажи, что демо-вакансии и демо-кандидаты в seed —
синтетические, и что реальной интеграции с внешними системами в MVP нет.

### Тесты
Минимум: прохождение обоих основных сценариев на уровне сервисов, идемпотентность
апдейтов, проверка подписи initData. Не гонись за покрытием, покрой главный путь.

## 9. Порядок работы

1. План файлов → показать мне.
2. Скелет: compose поднимается, бот отвечает на `/start`, вебхук принимает апдейты.
3. Сценарий соискателя целиком (он короче и важнее для демо).
4. Сценарий работодателя в чате + создание вакансии.
5. Мини-приложение: список кандидатов и смена статуса.
6. Уведомления и слоты собеседования.
7. Seed с синтетическими данными.
8. Тесты, README, финальная проверка сборки по таймеру.

После каждого пункта — короткий отчёт, что сделано и что осталось. Не переходи к
следующему, пока предыдущий не проверяется вручную.
