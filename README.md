# Найм линейного персонала в MAX

Чат-бот с мини-приложением в мессенджере MAX: владелец кафе или магазина публикует вакансию и получает
отклики уже отфильтрованными по стоп-критериям, а соискатель откликается за минуту кнопками в чате.

Бот: [@t577_hakaton_max_bot](https://max.ru/t577_hakaton_max_bot) · трек «Эффективный бизнес», направление
«Кадры для бизнеса».

- **Исходный код:** https://github.com/Sorryprod/Max-personal-bot (ветка `main`; зафиксированный commit hash —
  на первом слайде презентации и в `SUBMISSION.txt` архива сдачи).
- **Команда Gaszstr:** Данил Зиновьев — фулстек-разработчик, Александр Ляшов — тестировщик,
  Кристина Мотрук — продакт-менеджер.

Сценарий доступен в мобильных клиентах MAX (iOS, Android) и в веб-версии: чат-бот и мини-приложение используют
только кросс-платформенные возможности (inline-кнопки, deep link, MAX Bridge). Функции, которых может не быть
в конкретном клиенте (вибрация, «Поделиться в MAX»), проверяются перед вызовом и имеют запасной вариант.

**Быстрый старт:** `./install.sh` (Linux, macOS, Git Bash) или
`powershell -ExecutionPolicy Bypass -File .\install.ps1` (Windows) — скрипт спросит токен бота и способ
публикации, заполнит `.env` и поднимет всё в Docker. Подробнее — в разделе про запуск.

## Назначение решения

**Проблема.** Владелец небольшой точки (кафе, магазин; 1–3 точки, без HR-отдела) в Белгородской области ищет
линейный персонал — повара, продавца, официанта, курьера. Отклики приходят вразнобой: звонки, городские чаты,
личные сообщения. Часть теряется, а базовые вопросы (возраст, медкнижка, готовность к графику) приходится
выяснять вручную с каждым. Соискатель на линейную позицию не заполняет длинные формы и не получает ответа.

**Решение.** Путь «вакансия → отклик → скрининг → приглашение на собеседование» целиком в MAX:

- работодатель создаёт вакансию в мини-приложении и получает ссылку-приглашение, которую пересылает в любой чат
  (в том числе кнопкой «Поделиться в MAX»);
- соискатель по ссылке попадает в бота, отвечает на 1–3 отсеивающих вопроса кнопками, оставляет имя и телефон;
- работодатель получает уведомление, сравнивает кандидатов на одном экране и ставит статус;
- при приглашении кандидат выбирает время собеседования из 2–3 предложенных слотов кнопкой; обе стороны
  получают подтверждение.

**Сознательно не делаем** (Won't Have): чат между сторонами, резюме и файлы, оплату, геопоиск, многопользовательские
аккаунты работодателя, аналитику, LLM. Интеграция с «Работой России» — следующий шаг, в MVP её нет.

## Основной пользовательский сценарий

**Работодатель**

1. Открывает бота, выбирает «Я ищу сотрудников».
2. Бот спрашивает название точки и город (города Белгородской области — кнопками, либо текстом).
3. Кнопка «Создать вакансию» открывает мини-приложение: должность, график, зарплатная вилка, адрес и до 3
   отсеивающих вопросов (шаблоны или свои: «да/нет», варианты, свободный ответ; для отсеивающих отмечаются
   подходящие ответы). Черновик формы сохраняется, если закрыть приложение.
4. После публикации — экран со ссылкой-приглашением и кнопками «Поделиться в MAX» / «Скопировать ссылку»;
   ссылка дублируется в чат с ботом.
5. На каждый отклик приходит уведомление с ответами кандидата и пометкой, если он не прошёл отсев.
6. В мини-приложении «Мои вакансии и кандидаты»: фильтры по статусам, карточки или таблица сравнения, статусы
   «пригласить», «в резерв», «отказать».
7. «Пригласить» — выбор 2–3 вариантов даты и времени; кандидату уходит приглашение с адресом.

**Соискатель**

1. Переходит по ссылке-приглашению `https://max.ru/<бот>?start=<код>` и попадает в бота.
2. Видит карточку вакансии и кнопку «Откликнуться».
3. Отвечает на вопросы кнопками, указывает имя (можно одной кнопкой взять из профиля) и телефон
   (кнопка «Поделиться номером» или текстом). Перед отправкой телефона видит, кому и зачем он передаётся.
4. Получает подтверждение отклика; при смене статуса — уведомление; при приглашении выбирает время кнопкой.
5. `/my` — статусы своих откликов, `/privacy` — какие данные хранятся, `/delete` — удалить свои данные.

## Состав и архитектура решения

```
            MAX (клиенты iOS / Android / web)
               │  апдейты (webhook или long polling)      ▲  сообщения, клавиатуры (Bot API)
               ▼                                          │
┌──────────────────────────── api (FastAPI, один контейнер) ─────────────────────────────┐
│  app/max/        единственное место, знающее формат MAX: клиент Bot API (таймауты,     │
│                  ретраи), разбор апдейтов, клавиатуры, вебхук, long polling            │
│  app/bot/        диалог: роутер, конечный автомат (состояние в БД), обработчики        │
│                  работодателя / соискателя / данных пользователя, тексты               │
│  app/services/   предметная логика: скрининг, вакансии, отклики, собеседования,        │
│                  уведомления, удаление данных — не зависит от мессенджера               │
│  app/api/        REST для мини-приложения + проверка подписи initData                  │
│  /app/           статика мини-приложения (React + Vite + MAX UI + MAX Bridge)          │
└────────────────────────────────────────┬───────────────────────────────────────────────┘
                                         │ SQLAlchemy async
                                   ┌─────▼─────┐
                                   │ PostgreSQL │  миграции Alembic применяются при старте
                                   └───────────┘
```

Ключевые решения:

- **Изоляция платформы.** Бизнес-логика работает с нейтральными типами из `app/messaging.py`
  (`IncomingEvent`, `OutMessage`, `Button`); перевод в формат MAX — только в `app/max/`.
- **Состояние диалога в БД** (`dialog_state`), а не в памяти: перезапуск контейнера не ломает незавершённую анкету;
  при повторном переходе по ссылке отклик продолжается с того же вопроса.
- **Идемпотентность.** В MAX у апдейтов нет `update_id`, поэтому ключ строится из `mid` сообщения, `callback_id`
  нажатия или `user_id + timestamp` для `bot_started`; ключ пишется в `processed_update` в той же транзакции,
  что и изменения. Повторная доставка не создаёт второй отклик.
- **Outbox.** Сообщения копятся во время обработки и отправляются только после коммита. Если обработчик упал —
  транзакция откатывается, пользователь получает «попробуйте повторить», шаг диалога не сдвигается.
- **Вызовы MAX API** обёрнуты в таймаут и ретрай (сетевые ошибки, 429, 5xx); ошибка отправки не роняет обработку.
- **Разделение бот / мини-приложение** по рекомендациям трека: вопросы, статусы, уведомления и выбор слота — в чате;
  длинная форма, список, сравнение кандидатов и возврат к данным — в мини-приложении.

Структура репозитория:

```
app/            бэкенд (см. схему выше); app/db/seed.py — синтетические демо-данные
migrations/     Alembic
webapp/         мини-приложение (React, TypeScript, Vite)
tests/          pytest: сценарии, API, initData, идемпотентность, данные
certs/          публичный корневой сертификат Минцифры (им подписан TLS API MAX)
docs/           openapi.json — описание REST API мини-приложения
Dockerfile      3 стадии: сборка фронта → Python-зависимости → рантайм
compose.yaml    сервисы api, db (+ необязательный tunnel)
install.sh      интерактивная настройка .env и запуск (install.ps1 — то же для Windows PowerShell)
```

**Собственного API для внешней проверки нет.** REST `/api/*` — внутренний бэкенд мини-приложения: каждый запрос
авторизуется подписью `initData` (или токеном запасного входа), выданной MAX конкретному пользователю, поэтому
отдельных тестовых учётных записей и `DATA-API.yaml` нет. `docs/openapi.json` приведён как справочное описание
контракта между мини-приложением и бэкендом.

## Одна команда запуска всех локальных компонентов через Docker

```bash
cp .env.example .env    # заполнить BOT_TOKEN (и остальное — см. ниже)
docker compose up -d --build
```

Поднимаются `db` (PostgreSQL 16) и `api` (бот + REST + мини-приложение); миграции и демо-данные применяются
автоматически. Проверка: `curl http://localhost:8080/health` → `{"status":"ok"}`.

Если нужен публичный HTTPS-адрес (вебхук и мини-приложение в MAX) — необязательный туннель CloudPub:
`docker compose --profile tunnel up -d --build` (нужен `CLOUDPUB_TOKEN`; адрес — в `docker compose logs tunnel`).

### Запуск через скрипт установки (рекомендуется для проверки)

```bash
./install.sh                                             # Linux, macOS, Git Bash на Windows
powershell -ExecutionPolicy Bypass -File .\install.ps1   # Windows PowerShell
```

Скрипт проверяет Docker, создаёт `.env` из `.env.example` (со случайным паролем БД), спрашивает `BOT_TOKEN` и
способ публикации, выставляет режимы и запускает стек, дожидаясь готовности `api`:

| Вариант | Что нужно | Что получится |
|---|---|---|
| 1. Туннель CloudPub (по умолчанию) | бесплатный аккаунт [cloudpub.ru](https://cloudpub.ru) и его токен (`CLOUDPUB_TOKEN`) | скрипт сам берёт адрес туннеля из логов, пишет его в `PUBLIC_URL`, включает вебхук; доступен весь сценарий, включая мини-приложение |
| 2. Свой HTTPS-адрес | домен с доверенным сертификатом на 443, проксирующий на `localhost:8080` | то же, адрес вводится вручную |
| 3. Только чат-бот | ничего | long polling без публичного адреса: проверяется сценарий соискателя; мини-приложение работодателя недоступно |

Для вариантов 1–2 скрипт спрашивает, прописан ли URL `PUBLIC_URL/app/` в настройках бота в кабинете MAX для
бизнеса. Если нет (у проверяющего обычно нет доступа к кабинету бота) — ставится `WEBAPP_OPEN_MODE=link`: кнопки
бота открывают мини-приложение по ссылке с подписанным токеном, весь сценарий работодателя проходится так же,
но функции MAX Bridge («Поделиться в MAX», системная кнопка «Назад», вибрация) недоступны — вместо шеринга
работает «Скопировать ссылку». В настройках бота хакатона прописан адрес авторского стенда.

Повторный запуск скрипта безопасен: заданные значения предлагаются по умолчанию (Enter — оставить).

> **Один токен — один запущенный экземпляр.** MAX доставляет апдейты бота только в одно место: при старте
> экземпляр снимает чужие подписки и ставит свою (вебхук) или забирает апдейты сам (polling). Если с тем же
> токеном запущен другой стенд, остановите его: иначе апдейты будут уходить туда, а данные разойдутся по разным базам.

## Необходимые параметры окружения

- Docker Engine 24+ с Docker Compose v2.
- Исходящий доступ в интернет к `platform-api2.max.ru:443` (MAX Bot API) и `st.max.ru` (скрипт MAX Bridge
  загружается клиентом мини-приложения).
- Токен бота MAX.
- Для полного сценария в MAX (вебхук и мини-приложение) — публичный HTTPS-адрес на порту 443 с доверенным
  сертификатом (свой домен или туннель, например CloudPub), указанный в `PUBLIC_URL`, и URL
  `PUBLIC_URL/app/` в настройках бота в кабинете MAX для бизнеса.
  Без публичного адреса работает чат-бот в режиме `UPDATES_MODE=polling`.
- Свободный порт `8080` на хосте (меняется через `API_PORT`).

## Используемые порты

| Порт | Где | Назначение |
|---|---|---|
| `8080` (хост, `API_PORT`) → `8080` (контейнер `api`) | HTTP | `/max/webhook` — вебхук MAX; `/api/*` — REST мини-приложения; `/app/` — мини-приложение; `/health` |

## Внешние сервисы и интеграции

- **MAX Bot API** (`https://platform-api2.max.ru`): `GET /me`, `POST /messages`, `POST /answers`,
  `GET /updates`, `GET|POST|DELETE /subscriptions`, `PATCH /me/commands`. TLS API подписан корневым
  сертификатом Минцифры — он лежит в `certs/` и добавляется к доверенным при запросах (проверка TLS не отключается).
- **Возможности MAX, которые использует продукт:**
  - ссылки-приглашения с параметром `?start=<код>` (deep link в бота);
  - inline-клавиатуры: callback-кнопки, `request_contact` (поделиться номером), `open_app` (мини-приложение),
    `link`, `clipboard` (скопировать ссылку);
  - редактирование сообщения при ответе на нажатие: клавиатура убирается, под вопросом остаётся «✓ ответ»;
  - меню команд бота (`/start`, `/my`, `/privacy`, `/delete`);
  - мини-приложение: авторизация по подписанному `initData`, параметр `startapp`, системная кнопка «Назад»;
  - **«Поделиться в MAX»** (`WebApp.shareMaxContent`) — работодатель одним нажатием отправляет готовое объявление
    со ссылкой-приглашением в городской чат вакансий: это основной канал, где ищут линейный персонал.
    Кнопка показывается только внутри клиента MAX; если шеринг недоступен, ссылка копируется в буфер;
  - тактильный отклик (`HapticFeedback`) при публикации вакансии и отправке приглашения.
- **HTTPS-туннель CloudPub** (необязательно) — публичный адрес для вебхука и мини-приложения без собственного
  сервера. Внутри Docker не воспроизводится как внешний сервис: нужен аккаунт CloudPub и `CLOUDPUB_TOKEN`.
  Можно заменить любым reverse-proxy с доверенным сертификатом на 443.
- **Внешних информационных систем (Работа России, HR-системы и т. п.) в MVP нет.**

## Описание работы с данными

- **Хранилище:** PostgreSQL. Таблицы: `employer`, `vacancy`, `screening_question`, `candidate`, `application`
  (статусы `new → screened → invited / reserve / rejected`), `answer`, `interview_slot`, `dialog_state`
  (шаг и контекст диалога, JSONB), `processed_update` (ключи обработанных апдейтов).
- **Что хранится о людях:** у соискателя — имя, телефон, ответы, статус отклика, время собеседования и момент
  согласия на передачу данных работодателю (`candidate.consent_at`); у работодателя — имя из профиля MAX,
  название точки, город, вакансии.
- **Доступ:** соискатель видит только свои отклики; работодатель — только свои вакансии и отклики на них
  (чужие id отдают 404). Пользователь в API определяется только по проверенной подписи `initData`
  (HMAC-SHA256 от токена бота, проверка срока `auth_date`), а не по переданному `user_id`.
- **Удаление:** `/delete` в боте удаляет все данные пользователя (после подтверждения). `/privacy` — описание.
- **Время** хранится в UTC, показывается в `APP_TIMEZONE`.
- **Секреты** — только в переменных окружения; в коде и истории git их нет.
- **Демо-данные — синтетические.** Вакансии, точки, кандидаты и телефоны в `app/db/seed.py` вымышлены:
  у демо-кандидатов отрицательные `max_user_id` (у реальных пользователей MAX таких не бывает), бот им ничего
  не отправляет; телефоны — из тестового диапазона `+7 900 000-00-xx`. Реальной интеграции с внешними
  системами в MVP нет.

## Порядок работы с тестовыми данными

- При старте (`SEED_DEMO=true`) загружаются две демо-вакансии с синтетическими кандидатами:
  `https://max.ru/<бот>?start=demo-povar` (3 отсеивающих вопроса) и `…?start=demo-prodavec`.
  Повторный старт ничего не дублирует.
- **Посмотреть работу с кандидатами без сбора откликов:** новый работодатель без вакансий видит в меню бота
  кнопку «Посмотреть на примере» — в его аккаунте создаётся вакансия «… (пример)» с четырьмя вымышленными
  кандидатами (двое не проходят отсев).
- Сбросить демо-данные к исходному состоянию (удаляются демо-вакансии, копии-примеры, синтетические кандидаты
  и их отклики; реальные вакансии не затрагиваются):
  `docker compose exec api python -m app.db.seed --reset`
- Сделать себя владельцем демо-вакансий (чтобы получать уведомления по ним):
  `docker compose exec api python -m app.db.seed --owner <ваш MAX user_id>`
- Полностью чистая база: `docker compose down -v && docker compose up -d --build`.
- Автотесты: `pip install -r requirements-dev.txt && pytest` (SQLite в памяти, внешние вызовы подменены; 56 тестов:
  оба сценария на уровне сервисов, идемпотентность апдейтов, проверка подписи initData, доступ к данным,
  приглашение и слоты, удаление данных, демо-данные).

## Пошаговый сценарий проверки

Для одного аккаунта MAX обе роли доступны одновременно — можно проверить весь путь в одиночку.

1. Запустить решение `./install.sh` (вариант 1 — туннель CloudPub) или вручную с публичным `PUBLIC_URL` и
   `UPDATES_MODE=webhook`. Если URL `PUBLIC_URL/app/` не прописан в настройках бота — `WEBAPP_OPEN_MODE=link`,
   в шаге 5 вместо «Поделиться в MAX» используется «Скопировать ссылку».
2. **Соискатель.** Открыть `https://max.ru/<бот>?start=demo-povar` → «Откликнуться» → ответить кнопками
   (на «медкнижку» ответить «Нет») → имя кнопкой из профиля → «Поделиться номером».
3. **Работодатель.** `/start` → «Я ищу сотрудников» → название точки → город кнопкой → «Посмотреть на примере».
4. «Мои вакансии и кандидаты» → вакансия «(пример)» → переключить «Карточки / Сравнение» → у кандидата
   «В резерв», у другого «Отказать» (второе нажатие подтверждает).
5. «Создать вакансию» → заполнить форму с 1–2 вопросами из шаблонов → «Опубликовать» → «Поделиться в MAX»
   (или «Скопировать ссылку»).
6. Открыть полученную ссылку как соискатель и пройти отклик — работодателю приходит уведомление.
7. В мини-приложении у этого отклика «Пригласить» → «Отправить» (время подставлено) → в чате соискателя выбрать
   время кнопкой → обе стороны получают подтверждение, в карточке кандидата видно время собеседования.
8. `/my` — статусы откликов; `/privacy` — какие данные хранятся.
9. `/delete` → «Удалить»: удаляются данные обеих ролей этого аккаунта. Повторить шаги 2–8 — сценарий проходится
   заново (для полностью чистой базы — `docker compose down -v && docker compose up -d --build`).

## Примеры ожидаемого поведения системы

| Действие | Ожидаемый результат |
|---|---|
| Соискатель открывает ссылку-приглашение | карточка вакансии (зарплата, график, адрес) и кнопка «Откликнуться» |
| Пишет текст вместо нажатия кнопки на вопросе | «Пожалуйста, выберите вариант кнопкой…» и тот же вопрос снова; «да»/«нет» текстом принимаются |
| Вводит имя «А1» или телефон «позвоните мне» | объяснение формата и повторный запрос, анкета не сбрасывается |
| Уходит из анкеты и возвращается по ссылке | «продолжим с того же места», следующий неотвеченный вопрос |
| Повторно открывает ссылку после отклика | «Вы уже откликались… Статус: …» |
| Нажимает старую кнопку уже пройденного вопроса | всплывающее «Этот вопрос уже пройден», ничего не меняется |
| Отклик отправлен | подтверждение соискателю; работодателю — «Новый отклик» с ответами и пометкой об отсеве |
| Работодатель ставит «В резерв» / «Отказать» | соискателю приходит вежливое сообщение; повторная установка того же статуса не дублирует его |
| Работодатель отправляет приглашение | соискателю — адрес и кнопки со временем; после выбора — подтверждение обеим сторонам |
| Работодатель меняет время или отказывает | старые кнопки времени отвечают «Это приглашение больше не действует» |
| Ссылка на закрытую вакансию | «Вакансия не найдена или уже закрыта» |
| Форма вакансии с ошибками | подсветка полей и понятные сообщения («Зарплата «от» больше, чем «до»») |
| Мини-приложение открыто не из MAX / подпись неверна | экран «Откройте из чата с ботом» / 401, данные не отдаются |
| Нет сети в мини-приложении | состояние ошибки с кнопкой «Попробовать ещё раз» |
| Повторная доставка апдейта MAX | обрабатывается один раз |
| Внутренняя ошибка в обработчике | пользователю — «попробуйте повторить», без трейсбека; шаг диалога сохранён |

## Известные ограничения

- Для нативного открытия мини-приложения URL `PUBLIC_URL/app/` должен быть прописан в настройках бота в кабинете
  MAX для бизнеса (из кода это не делается). Пока его нет — `WEBAPP_OPEN_MODE=link`: кнопки открывают ту же
  страницу по ссылке с подписанным токеном во встроенном браузере; функции MAX Bridge там недоступны.
- Вебхук MAX принимает только HTTPS на порту 443 с доверенным сертификатом; при локальном запуске без публичного
  адреса используется long polling. В режиме polling апдейт, пришедший во время недоступности БД, может быть потерян
  (в режиме webhook MAX доставит его повторно).
- Бот работает только в личных диалогах, не в групповых чатах.
- Один аккаунт MAX — один работодатель (без совместного доступа нескольких управляющих к точке).
- Один часовой пояс на развёртывание (`APP_TIMEZONE`).
- Выбранное кандидатом время меняет только работодатель («Перенести»); кандидат может ответить «Ни одно время
  не подходит» до выбора.
- Недоставленные уведомления (сбой MAX API после ретраев) логируются, но не переотправляются позже.
- При удалении данных соискателем работодатель не получает отдельного уведомления — отклик просто исчезает из списка.
- Формулировка согласия на передачу персональных данных сделана для MVP и не проходила юридическую проверку.
- Публичный адрес через бесплатный туннель зависит от работы компьютера, на котором запущен стек.
- С одним токеном бота одновременно работает только один экземпляр решения (см. «Один токен — один экземпляр»).
- `shareMaxContent` и тактильный отклик работают только в клиентах, которые их поддерживают (в вебе вибрации нет).

## Порядок остановки и повторного запуска

```bash
docker compose stop                 # остановить, данные сохраняются
docker compose start                # запустить снова
docker compose down                 # удалить контейнеры, данные БД сохраняются в томе pgdata
docker compose up -d --build        # поднять заново (миграции применятся автоматически)
docker compose down -v              # удалить контейнеры и все данные (чистая база)
docker compose logs -f api          # логи бота и API
```

С туннелем — добавить `--profile tunnel` к `up`/`down`. Конфигурация туннеля хранится в томе `cloudpub-config`,
поэтому публичный адрес сохраняется между перезапусками; `down -v` его сбрасывает (адрес изменится — его нужно
заново указать в `PUBLIC_URL` и в настройках бота). При смене режима или адреса бот сам переподписывает вебхук при старте.
